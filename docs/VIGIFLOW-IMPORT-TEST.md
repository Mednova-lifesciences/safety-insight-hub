# VigiFlow validated-import test — procedure and result capture

**Current status: NOT PERFORMED.** No VigiFlow import has been run against
any file this pipeline produces. Nothing in this repository may be read as
evidence that VigiFlow accepts these files.

This document exists to make that statement falsifiable: it names the file
to submit, the steps, and exactly what to paste back here afterwards.

## The four levels of verification, and which we have

These get conflated constantly, so they are spelled out:

| Level | Meaning | Status |
|---|---|---|
| **Mapped** | The source value reaches the normalized model | Yes — covered by `source-to-xml-coverage.test.ts`, `sample-source-coverage.test.ts` |
| **Serialized** | It reaches the XML in the right E2B(R3) element | Yes — asserted against the serialized bytes, not the model |
| **Schema-valid** | The file validates against the official ICH XSD | Yes — 12/12 artifacts against `MCCI_IN200100UV01.xsd` from `ICH_ICSR_XML_Schema_Set_v2.5.zip` |
| **VigiFlow-validated** | UMC's validated import accepted it | **No. Not attempted.** |

A TypeScript property existing is not any of these. Schema validity is not
acceptance: the XSD cannot check a codelist binding, a conditional
requirement, or a business rule, and VigiFlow checks all three.

## Prerequisites the preflight already enforces

`validateVigiFlowPreflight` (per case) and `validateVigiFlowBatch` (per
file) check these before an export is offered. They are what we believe a
validated import requires; the import itself is the authority, and any
divergence found in the test below should be corrected here.

| Prerequisite | E2B | Check | Severity |
|---|---|---|---|
| Report type | C.1.3 | `VIGIFLOW-REPORT-TYPE-MISSING` | BLOCKING |
| Reporter qualification | C.2.r.4 | `VIGIFLOW-REPORTER-QUALIFICATION-MISSING` / `-UNRESOLVED` | BLOCKING |
| Reporter named | C.2.r.1 | `VIGIFLOW-REPORTER-NAME-ABSENT` | INFO |
| Patient identifier | D.1 / D.1.1 | `VIGIFLOW-PATIENT-RECORD-NUMBER-ABSENT` | INFO |
| ≥1 MedDRA-coded reaction | E.i.2.1b | `VIGIFLOW-MEDDRA-MISSING` | BLOCKING |
| ≥1 suspect drug | G.k.1 | `VIGIFLOW-SUSPECT-DRUG-MISSING` | BLOCKING |
| ≤100 ICSRs per file | — | `VIGIFLOW-BATCH-TOO-LARGE` | BLOCKING |

Two of these deserve a note rather than silent compliance:

- **Reporter identifier.** E2B(R3) defines no reporter identifier element.
  UMC documentation names a "reporter identifier" but does not map it to
  an E2B element. We therefore treat an identifiable reporter as a *named*
  one (C.2.r.1) and record this as an open question for the import test to
  settle — see "Questions the test should answer" below.
- **MedDRA coding** is currently BLOCKING for every case, because no
  licensed MedDRA provider is configured. That is the honest state: a
  reaction cannot be coded without a dictionary. It also means no file can
  presently pass preflight with real coded reactions, which the test
  procedure has to work around (step 2).

## Procedure

**1. Produce the file.**

The known-good artifact is `artifacts/e2b-r3/test-outcome-batch.xml` — a
realistic ten-case AEFI batch exercising all six E.i.7 outcomes, with real
vaccine names, batch numbers, dates and reporter designations. It is
regenerated by `npx vitest run src/services/e2b-r3/outcome-batch.test.ts`
and validates against the ICH XSD.

For a submission test, prefer a file exported through the product itself
(E2B page → *Download validated E2B*) so the test exercises the real path
including transmission configuration.

**2. Satisfy the coded-reaction prerequisite.**

A validated import needs MedDRA-coded reactions. Either configure a
licensed MedDRA provider, or — if the purpose is to test the structure
rather than the coding — agree with UMC that the test file may carry
uncoded terms, and record that agreement here.

**3. Check the file size.** At most 100 ICSRs. `splitIntoBatches()`
already enforces this; confirm the file you are submitting is one batch.

**4. Submit** through VigiFlow's validated import for the test/sandbox
environment. **Do not submit real patient data to a test environment**, and
do not submit synthetic data to production. The Ondo file contains real
patient names and must not be used here.

**5. Capture the result below**, verbatim. An error list is more valuable
than a pass, and a paraphrase is worth nothing.

## Questions the test should answer

Each of these is a real uncertainty in the current implementation. The
import result is the authority that settles it.

1. **Reporter identifier** — does the import require anything beyond
   C.2.r.1, and if so, which element does it read?
2. **C.1.1 format** — this pipeline now exports the source's own case
   identifier verbatim (`OG-901`, `OG/AEFI/2026/0413`), not a
   country-organisation-qualified one. Does the import accept a bare
   facility identifier, and does it accept `/` in the extension?
3. **Uncoded reactions** — is `nullFlavor="UNK"` with `<originalText>`
   accepted, or rejected outright?
4. **Uncoded route** — same question for `<routeCode nullFlavor="UNK">`
   with `<originalText>`.
5. **D.2.3 age group** — is it accepted when present, and is it rejected
   or ignored when a precise age is also present?
6. **Dosage text** — is `<text>` accepted as G.k.4.r.8 where this
   serializer places it?
7. **Sender/receiver identifiers** — which values does the receiving
   organisation actually expect?

## After the test

Whatever the import reports:

- Correct `validateVigiFlowPreflight` so the next export catches the same
  problem *before* submission.
- Add a regression test for each error the import returned.
- Update the status line at the top of this document.

Until that has happened, the correct description of this work remains
"schema-valid, not VigiFlow-validated".
